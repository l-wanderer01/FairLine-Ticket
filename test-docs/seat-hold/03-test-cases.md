# 테스트 케이스

모든 케이스의 초기 상태는 NOT_RUN이다. 정상 fixture와 격리 환경은 공통 사전 조건이며, 케이스마다 재설정한다. 아래 기대 결과는 현재 동작 특성 또는 목표 불변 조건을 명시한다. 정책 미결정의 처리 방법은 테스트 기준 문서를 따른다.

## 선점·해제·입력

| ID / 우선순위 / 수준 | 사전 조건 | 실행 절차 | 기대 결과 및 검증 |
| --- | --- | --- | --- |
| TC-01 / P0 / 통합·HTTP | S01 비어 있음 | U-A가 S01 단일 선점 | 200 held; owner=A, 양수 TTL≤5분, A 목록에 S01; DB 좌석은 AVAILABLE |
| TC-02 / P0 / 통합·HTTP | A가 S01 선점 | B가 S01 선점 | 409; owner=A, TTL 갱신 없음, B 목록에 S01 없음 |
| TC-03 / P0 / 통합 | S01 비어 있음 | 서로 다른 사용자 100명이 barrier 후 S01 동시 선점 | held 성공 정확히 1명; 나머지 충돌; 최종 owner가 성공 사용자; 예기치 않은 5xx 없음 |
| TC-04 / P1 / HTTP | S01 비어 있음 | A 단일 선점 성공 후 동일 요청 재전송. 응답 유실 재시도도 재현 | 현재 특성: held→released, owner·목록 제거. POL-01 목표 판정은 결정 후. 더블클릭 동시는 별도 반복하고 결과 기록 |
| TC-05 / P0 / 통합 | A가 S01 선점 | B 해제 → A 해제 → A 재해제 | B 409 및 소유권 유지; A 200 released; 재해제 200 already_released; 최종 키·참조 없음 |
| TC-06 / P0 / 통합 | A가 S01~S04 선점 | A가 S05 추가 시도 | 400, 기존 4석 유지, S05 미선점 |
| TC-07 / P0 / 통합 | A의 선점 없음 | A가 S01~S08에 단일 요청 동시 실행 | held 성공 정확히 4개, 나머지 제한 오류; 최종 유효 선점·목록 4개 |
| TC-08 / P1 / HTTP | JWT 없음/만료 JWT/유효 JWT만 준비 | hold·holds·해제를 각 인증 조건으로 호출 | 무인증·만료 JWT는 401 및 변경 없음. 입장 키 없는 유효 JWT는 현재 동작 관찰; POL-05 결정 후 허용/거부 판정 |
| TC-09 / P1 / HTTP | 기본 fixture | 필수 필드 누락, 빈 목록, 5개 목록, [S01,S01], 중복 포함 5개 목록, null 원소, 없는 좌석, 판매 좌석, 회차 불일치 요청을 각각 실행 | 필수/빈/원본 5개는 400; 길이 2의 중복은 1석만 선점; 없는 단일 좌석 404, 판매 단일 좌석 409; 잘못된 일괄 좌석 409. null 원소는 미선점 및 4xx 목표; 모든 실패에 부작용·예기치 않은 5xx 없어야 함 |

## 일괄 선점·만료

| ID / 우선순위 / 수준 | 사전 조건 | 실행 절차 | 기대 결과 및 검증 |
| --- | --- | --- | --- |
| TC-10 / P0 / 통합·HTTP | S01~S04 비어 있음 | A가 4석 일괄 선점 | 200, heldSeatIds 집합 일치, 4석 owner=A·양수 TTL, 목록 4개 |
| TC-11 / P0 / 통합 | A가 S01, B가 S03 선점 | A가 [S01,S02,S03] 요청 | 409, 신규 S02 없음, A의 기존 S01과 B의 S03 유지; POL-02 제안 기준 |
| TC-12 / P0 / 통합 | 비어 있음 | A [S01,S02], B [S02,S03] 일괄 요청을 동시 실행 | 공유 S02 소유자 1명; 성공 요청은 전체 확보, 실패 요청의 신규 선점 잔여 없음. 실제로 경합이 일어났는지 로그 확인 |
| TC-13 / P1 / 통합 | A가 S01~S03 선점 | A가 [S04,S05] 일괄 요청 | 400; S04·S05 신규 선점 없음; 기존 3석 유지 |
| TC-14 / P1 / 통합·HTTP | 기본 fixture | [S01,S10], C-A로 [S01,S11] 각각 요청 | 다른 회차는 400, 다른 공연 좌석은 409; 어느 좌석도 신규 선점 없음 |
| TC-15 / P0 / 통합 | A가 4석 선점 | 실제 만료까지 기다리고 B가 S01, A가 S05 선점 | B 재선점 성공; A stale 참조 정리 후 S05 성공; 유효 선점 기준 4석 이하; 만료 자체가 사용자 set을 즉시 삭제한다고 가정하지 않음 |
| TC-16 / P0 / 통합 | A 선점 만료 직전 | A의 해제를 owner 조회 직후 일시정지 → TTL 만료 → B 재선점 → A 해제 재개 | Lua 소유자 확인으로 B 키·목록 유지. A의 응답과 TTL 기록; INV-03 |

## 예약·확정·정리

| ID / 우선순위 / 수준 | 사전 조건 | 실행 절차 | 기대 결과 및 검증 |
| --- | --- | --- | --- |
| TC-17 / P0 / 통합·HTTP | A가 S01,S02를 서로 다른 시점에 선점 | A 예약 생성 | 201 HOLDING; 항목 2개, 총액 20000, 만료는 관측 최소 TTL 기반. DB now/앱 now/TTL 관측 시각 기록, 초 단위 절삭과 측정 시간 오차 구분 |
| TC-18 / P0 / 통합 | A 선점 없음/타인 선점/만료/판매 좌석 | 각 조건에서 A 예약 생성 | 거절되고 예약·항목 추가 없음; Redis 변경 없음. HTTP 상태는 실제 공통 예외 매핑도 검증 |
| TC-19 / P0 / 통합 | A가 S01 선점 | A의 같은 예약 요청 2개를 충돌 조회 완료 후 barrier로 동시에 저장 진행 | 유효한 예약 최대 1개; 실패 응답 또는 동일 예약 반환. 별개 HOLDING 2개면 FAIL; 트랜잭션별 커넥션 필요 |
| TC-20 / P0 / 통합 | A의 S01 HOLDING 예약 | A Redis/DB 만료 → B 재선점·예약 → A 늦은 확정 → B 확정. 역순도 실행 | 동일 좌석 CONFIRMED 최대 1개; 성공 확정은 좌석 확보와 일치. 늦은 결제 수용 상세는 POL-04; 2건 확정이면 즉시 FAIL |
| TC-21 / P0 / 통합 | A의 유효 HOLDING | 확정 요청 1회 후 동일 확정 반복·동시 실행 | 최초 CONFIRMED, 이후 ALREADY_CONFIRMED; 좌석 RESERVED; 팬 점수·outbox 업무 효과 중복 없음. ingress 기록 횟수와 업무 효과는 구분 |
| TC-22 / P0 / 통합 | A의 HOLDING | confirm과 cancel, confirm과 expire를 각각 barrier로 경합 | 예약 최종 상태 1개; CONFIRMED면 좌석 RESERVED, CANCELED면 다른 확정 소유권 훼손 없음; outbox와 상태 일치 |
| TC-23 / P0 / 통합 | A·B 접근 세션 각 1개, active=2; A 선점 | A leave 2개를 hadAccess 확인 지점에서 경합. 별도로 A leave와 A 확정 정리 경합 | A 선점·접근 제거, B 유지; active=1 정확히 한 번 감소. active=0이면 중복 차감 결함 |
| TC-24 / P1 / 통합 | A의 이전 HOLDING 예약을 만료시킨 뒤 A가 새 좌석 S02 선점 | 이전 예약 expire/cancel 정리 수행 | S02 제거 여부 관찰; POL-06 결정 후 판정. 새 세션의 선점 손실 위험을 결과에 명시 |

## 장애·확장

| ID / 우선순위 / 수준 | 사전 조건 | 실행 절차 | 기대 결과 및 검증 |
| --- | --- | --- | --- |
| TC-25 / P1 / 장애 통합 | [S01,S02] 일괄 요청 | S01 Lua 성공 직후 S02 호출에 Redis 오류 주입. 별도 실행에서 성공 직후 프로세스 강제 종료 | 거짓 성공 없음; 잔여 S01·목록·TTL 기록. 정상 충돌 보상과 예외 경로 구분; POL-02 복구 기한 미정이면 복구 판정 BLOCKED, 실제 TTL 만료 후 재선점 확인 |
| TC-26 / P0 / 다중 인스턴스 | 티켓팅 2개, 공유 Redis/DB | TC-03,07,12,19,20,23을 두 인스턴스로 나눠 반복 | 동일 불변 조건 유지; 각 인스턴스가 요청을 처리한 증거; 각 경쟁 케이스 최소 20회 반복 |
| TC-27 / P2 / 부하 | 정합성 P0 통과, 목표 미결정 | 단일 인기 좌석 집중/분산 좌석/겹치는 일괄 선점을 각각 단계적으로 부하 증가 | 처리량·p95/p99·정상 충돌률·5xx·timeout·DB pool 대기·Redis 지연·stale set 크기 기록. 불변 조건 위반은 FAIL; 성능 PASS는 POL-07 결정 후 |

TC-09는 입력 변형별, TC-18은 상태별, TC-22·25는 장애/경합 조합별로 결과 행을 나눈다. 동시성 테스트의 통과는 지정 실행에서 위반이 관측되지 않았다는 의미이며 모든 스케줄의 안전성을 증명하지 않는다.
